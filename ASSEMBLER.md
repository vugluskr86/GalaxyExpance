# Ассемблер PCVM

Этот документ описывает язык Assembly виртуального компьютера Pixel Cosmos,
машинный формат, host-инструменты на JavaScript и состояние self-hosted
инструментов, выполняющихся внутри PCVM.

## Модель сборки

Целевая цепочка сборки:

```text
source.asm
    │ assembler
    ▼
module.obj (PCOB v2)
    │ linker + libraries
    ▼
program.bin (PCVM v2)
    │ loader
    ▼
CPU
```

Host-цепочка реализована классами `Assembler` в `src/game/cpu.js` и
`AssemblyCompiler`/`Linker` в `src/game/toolchain.js`. Self-hosted цепочка
пишется на Assembly PCVM и хранится в `system/assembler.asm` и
`system/linker.asm`.

### Системные программы и общие Assembly-библиотеки

Установленные программы PCOS остаются отдельными исполняемыми файлами, даже
когда их короткий файл в `system/unix/bin/` выглядит только как `CALL`.
Например, `bin/grep.asm` экспортирует точку входа и вызывает `util_grep`, а
полная реализация разбора аргументов, чтения файла, поиска строк, `-n` и кода
завершения находится в `system/unix/lib/utilities.asm`. Скрипт
`scripts/build-unix-stage7-8.mjs` линкует эту библиотеку в **каждый** отдельный
`grep.bin`, `cat.bin`, `cp.bin` и другой бинарник; это не JavaScript-заглушки.

`system/unix/bin/scanner.asm` — самостоятельная protected-mode программа,
устанавливаемая как `/usr/bin/scanner.bin`. При запуске она переводит
бортовой терминал в графический режим и отрисовывает стартовый спектр PCVM
инструкциями `GFX_RECT`, затем вызывает `SCANNER_OPEN` (`SYSCALL 0x55`). Этот
ограниченный ABI-вызов разрешён только установленному компьютеру в активной
звёздной системе: он открывает интерактивный интерфейс сканирования с реальными
частотой, направлением антенны, шириной луча, поляризацией, RX/TX и записью
открытых данных. Вне системы вызов возвращает ошибку, не создавая вымышленных
результатов сканирования.

## Синтаксис

Регистр мнемоник и директив не учитывается. Операнды разделяются пробелами
или запятыми. Комментарий начинается с `;`.

```asm
start:
    LOAD_A 3
loop:
    DEC_A
    JNZ loop
    PRINT_A
    HALT
```

Поддерживаемые литералы:

- целые десятичные и шестнадцатеричные числа;
- отрицательные числа;
- числа с плавающей точкой;
- строки в двойных кавычках;
- имена символов.

SIMD-регистры записываются как `V0`–`V7`. Поддерживаются как общие формы
`VADD V0, V1`, так и совместимые алиасы `VADD_V0_V1`.

## Директивы

| Директива | Назначение |
|---|---|
| `.equ` | именованная константа |
| `.org` | установить адрес следующего блока данных |
| `.byte` | записать 8-битные значения |
| `.word` | записать 16-битные little-endian значения |
| `.dword` | записать 32-битные little-endian значения |
| `.string` | записать UTF-8 строку без завершающего нуля |
| `.zero` | зарезервировать и обнулить область |
| `.align` | выровнять следующий адрес данных |
| `.import` | объявить внешний символ |
| `.export` | экспортировать определённый символ |

Пример данных:

```asm
buffer_size: .equ 256
.org 4096
message: .string "Hello"
.byte 0
.align 4
counter: .dword 0
buffer: .zero buffer_size
```

## Символы и relocation

`PCOB v2` использует две фазы:

1. Первый проход назначает каждому символу секцию и относительное смещение.
2. Второй проход кодирует содержимое и создаёт relocation-записи.

Секции символов:

| Секция | Значение |
|---|---|
| `TEXT` | индекс инструкции относительно начала модуля |
| `DATA` | адрес относительно начала секции данных |
| `UND` | импортированный, ещё не разрешённый символ |

Relocation-запись содержит секцию места исправления, смещение, ширину,
имя символа и тип:

- `ABS_TEXT` — абсолютный индекс инструкции для `JMP`, `JZ`, `JNZ`, `CALL`;
- `ABS_DATA` — абсолютный адрес данных в операнде или таблице данных.

Линкер проверяет повторные экспорты, отсутствующие импорты и соответствие
секции. Например, `CALL` не может ссылаться на `DATA`.

## Форматы PCVM v2 и v3

Исполняемый файл начинается с:

```text
50 43 56 4D       "PCVM"
02                версия
uu uu             число инструкций, u16 LE
```

Обычные программы без protected-инструкций сохраняют этот формат. Protected
mode использует PCVM v3:

```text
50 43 56 4D       "PCVM"
03                версия
01 00             featureFlags: protected mode
uu uu             число инструкций, u16 LE
```

Директива `.protected` принудительно выбирает v3. Инструкции `PM_ENABLE`,
`PM_DISABLE`, `SET_UBASE`, `SET_ULIMIT`, `SET_KSP`, `SET_IVT`, `ENTER_USER`,
`SYSCALL`, `IRET`, `CLI` и `STI` включают protected feature автоматически.
Они занимают opcode `135–149`; legacy-таблица `1–134` не перенумеровывалась.
Kernel-only `KGET_FAULT`, `KGET_ARG`, `KCALL_HOST` и `SYSRET` обеспечивают
исполняемый Assembly syscall dispatcher без автоматического host-side `IRET`.

PCOB остаётся форматом v2: версия PCVM и feature flags находятся во вложенном
payload, поэтому ABI symbol/relocation tables не изменяется.

В PixelOS команда `asm` по умолчанию добавляет `.protected` к пользовательскому
исходнику. Shell и примеры используют `SYSCALL` для терминала, графики, ввода,
файлов, IPC и процессов. Прямые аппаратные инструкции остаются допустимыми в
BIOS, kernel mode и legacy PCVM v2, но создают `PRIVILEGE_FAULT` в user mode.

Инструкция:

```text
opcode:u8 argc:u8 operand...
```

Операнд числа кодируется как `type=0` и `Float64 LE`. Строковый операнд —
как `type=1`, `length:u16 LE`, UTF-8 bytes. После кода располагается список
инициализируемых сегментов данных.

Нормативная таблица всех 134 инструкций экспортируется из
`src/game/cpu.js` как `ISA_TABLE`. Для каждой строки зафиксированы
`opcode`, `name`, `argc`. Ассемблер и декодер отклоняют несовпадающую
арность. Существующие номера нельзя переставлять; новые инструкции можно
только добавлять после opcode 134.

## Что реализовано на JavaScript

- все 134 opcode и фиксированная арность;
- метки, прямые и обратные ссылки;
- проверка повторных меток и неизвестных мнемоник;
- перечисленные выше директивы данных;
- формирование и проверка `PCVM v2/v3` и feature flags;
- `PCOB v2` с таблицами `TEXT`, `DATA`, `UND`;
- двухпроходная таблица символов;
- relocation для `JMP`, `JZ`, `JNZ`, `CALL` и адресов данных;
- импорты и экспорты;
- статическая и динамическая линковка;
- проверка типа секции relocation;
- загрузка и выполнение бинарных файлов.

## Что реализовано self-hosted

Текущий `system/assembler.asm` является bootstrap-ассемблером:

- запускается как программа PCVM;
- читает имя и исходный файл с DRIVE;
- использует потоковый lexer;
- распознаёт таблицу из 134 legacy и 11 protected opcode;
- кодирует числовые и строковые операнды;
- записывает запускаемый файл `a.obj`;
- созданный файл проходит декодирование и исполняется CPU.

Для установленной Unix-системы генератор
`scripts/generate-unix-toolchain-cli.mjs` создаёт protected CLI-обёртки
`system/unix/bin/assembler.asm` и `system/unix/bin/linker.asm`. Они не являются
host-реализациями: внутри остаются те же self-hosted Assembly cores, но имя
входного файла берётся из `ARGS`, а I/O выполняется через `OPEN/READ/WRITE/CLOSE`
VFS syscalls. Генерируемые файлы нельзя редактировать вручную; проверка
воспроизводимости выполняется с `--check`.

CLI-linker разносит первый объект, второй объект и output workspace по памяти и
принимает объект до 240 КиБ. Системный Makefile использует единые translation
units для libc с программой, обходя известный дефект старого большого
multi-object relocation path.

Relocation для `LOAD_A`, `LOAD_B`, `LOAD_C`, `LOAD_D` теперь получает тип из
секции разрешённого символа: адрес обработчика/функции создаёт `ABS_TEXT`, адрес
данных — `ABS_DATA`. Это необходимо, в частности, для IVT ядра.

Ограничения текущей реализации:

- self-hosted multi-object linker принимает не более двух PCOB за запуск;
- архивный формат статических библиотек ещё не реализован;
- bootstrap assembler использует 2 МиБ RAM: выход уже разреженный, но
  промежуточные bytes пока размещаются как `data_image + virtualAddress`;
- linker повторно сканирует TEXT для каждой relocation, поэтому большие
  bootstrap-объекты линкуются квадратично.

### Текущий прогресс

Пункт 1 завершён. Таблица генерируется вспомогательным скриптом
`scripts/print-selfhost-isa.mjs` непосредственно из нормативной
`ISA_TABLE`; поэтому hash, opcode и argc можно проверять и обновлять без
ручного перенумерования. Интеграционный тест собирает self-hosted
ассемблер host-инструментом, запускает его в CPU и проверяет созданный им
бинарник, включая команду из поздней части таблицы.

Пункт 2 завершён. Реализованы отдельный symbol pass, записи
`{FNV-1a hash, section, value}`, секция `TEXT`, обнаружение повторного
определения, числовые константы `.equ`, записи `UND` для `.import`,
export-флаг и разрешение прямых и обратных ссылок без участия
JavaScript-компилятора. `.export name` разрешено располагать до `name:`:
placeholder `UND` при определении преобразуется в `TEXT` с сохранением
флага. Метка перед data-директивой преобразуется из предварительного
`TEXT` в `DATA`; `.org` задаёт базу, а `.dword` с несколькими значениями
увеличивает data offset на четыре байта для каждого элемента.

Интеграционный тест собирает `.import`, `.export`, `.equ`,
`JMP forward_label`, `.org 100`, `payload: .dword 1 2` и
`next: .dword 3` внутри VM. Значение `next` разрешается как адрес `108`.
Фактическая запись содержимого data-секций относится к пункту 4.

Потоковый `LEX_TOKEN` возвращает начало токена в `B`, конец в `D`, длину
в `A` и байт-разделитель в `FA`. Значение `FA=10` означает конец строки,
что позволяет первому проходу подсчитывать переменное число аргументов
директив данных.

Пункт 3 завершён. Второй проход ведёт отдельную таблицу relocation в RAM.
Запись занимает 16 байт:

```text
instruction:i32
operand:i32
type:i32
symbolHash:i32
```

Тип `1` соответствует `ABS_TEXT`, тип `2` — `ABS_DATA`. Для
`JMP`, `JZ`, `JNZ` и `CALL` создаётся `ABS_TEXT`; для символьного
адресного операнда другой инструкции — `ABS_DATA`. Константы `.equ`
подставляются непосредственно и relocation не создают. Для `UND`
кодируется placeholder `0`, но relocation сохраняет hash импортированного
символа. Сериализация этой RAM-таблицы в объект `PCOB v2` выполняется в
пункте 5.

Пункт 4 завершён. Self-hosted второй проход создаёт образ DATA в RAM и
сериализует его в настоящий сегмент `PCVM v2`.

- `.org` изменяет текущий адрес;
- `.byte`, `.word`, `.dword` принимают несколько значений до конца строки;
- `.word` и `.dword` записываются little-endian;
- `.string` копирует UTF-8 содержимое без окружающих кавычек;
- `.zero` оставляет заданное число нулевых байтов;
- `.align` дополняет образ нулями до кратного адреса;
- `.equ`, `.import`, `.export` обрабатываются таблицей символов.

DATA упаковывается в один сегмент от адреса 0 до максимального
использованного адреса. Промежутки от `.org`, `.zero` и `.align`
остаются нулевыми. Разделение разреженного образа на компактные сегменты
является последующей оптимизацией и не меняет семантику загрузки.

Пункт 5 завершён. Self-hosted ассемблер записывает бинарный `PCOB v2`:

```text
magic              4 bytes   "PCOB"
version            u8        2
payloadSize        u32 LE
symbolCount        u16 LE
relocationCount    u16 LE
payload            bytes     временный PCVM v2 с TEXT и DATA
symbols            16 bytes × symbolCount
relocations        16 bytes × relocationCount
```

Бинарная запись символа:

```text
hash:i32
section:i32        0=UND, 1=TEXT, 2=DATA, 3=CONST
value:i32
flags:i32          bit 0=import, bit 1=export
```

Host-объекты JavaScript сохраняют совместимый JSON body, а
`AssemblyCompiler.read()` автоматически различает JSON и бинарный
self-hosted вариант. Это позволяет постепенно перевести linker на
бинарный формат без нарушения существующих библиотек и программ.

Пункт 6 выполняется. Бинарный linker core в `src/game/toolchain.js`
завершён:

- назначает каждому модулю базы `TEXT` и `DATA`;
- объединяет несколько бинарных `PCOB v2`;
- строит глобальную таблицу экспортов по FNV-1a hash;
- разрешает локальные и внешние символы;
- применяет `ABS_TEXT` и `ABS_DATA`;
- проверяет повторный экспорт, отсутствующий символ, секцию и границы;
- выпускает статический `PCVM v2`;
- упаковывает динамический `PCDL v2`, разрешаемый при загрузке.

Создан `system/linker.asm`. Он запускается внутри PCVM, читает и проверяет
бинарный `PCOB v2`, проверяет magic, версию, полный ожидаемый размер,
границы payload и размеры таблиц. Затем он проходит symbol table и
отклоняет однообъектную сборку, если в ней остался `UND import`.
Разрешённый payload записывается как `a.bin`.
Интеграционный тест выполняет цепочку
`source.asm → self-hosted assembler → PCOB → self-hosted linker → PCVM`.
Отдельный отрицательный тест подтверждает, что объект с неразрешённым
импортом не создаёт исполняемый файл.

Добавлен self-hosted multi-object dynamic mode. Строка

```text
main.obj math.obj
```

заставляет `linker.asm` прочитать оба бинарных объекта и записать
`a.dyn` в бинарном формате `PCDL v2`:

```text
magic       4 bytes  "PCDL"
version     u8       2
count       u16 LE
objects     repeated { size:u32 LE, PCOB bytes }
```

Загрузчик проверяет границы контейнера, читает каждый `PCOB`, назначает
базы секций и применяет relocation. Интеграционный тест связывает
`main.obj` с `math.obj`; внешний `CALL double` выполняется и выводит
`42`.

До создания контейнера `linker.asm` теперь самостоятельно проходит
symbol tables обоих объектов. Для каждой записи с import-флагом он ищет
export с тем же FNV-1a hash в таблице второго объекта; проверка
выполняется в обе стороны. Неразрешённый import останавливает линковку до
записи файла. Отрицательный тест связывает `main.obj` с корректным
объектом без экспортов и подтверждает отсутствие `a.dyn`.

После разрешения imports линкер сравнивает экспортные множества обоих
модулей. Два export с одинаковым hash считаются конфликтом глобального
символа; линковка останавливается до создания контейнера. Этот случай
также покрыт отдельным отрицательным тестом.

Линкер вычисляет начало relocation table каждого объекта как
`symbolStart + symbolCount×16` и проходит обе таблицы внутри VM.
Допускаются только зафиксированные типы `1=ABS_TEXT` и `2=ABS_DATA`.
Неизвестный тип останавливает линковку; отрицательный тест подменяет тип
на `99` и проверяет, что выходной контейнер не создаётся.

Для каждой relocation self-hosted линкер теперь ищет target сначала среди
локальных определённых символов, затем среди exports второго объекта.
Номер типа relocation совпадает с требуемым id секции:
`ABS_TEXT=1 → TEXT=1`, `ABS_DATA=2 → DATA=2`. Несовпадение секции
останавливает линковку. Отрицательный тест предоставляет DATA-export для
`CALL` и подтверждает, что контейнер не создаётся.

Найденный target теперь не только проверяется: `linker.asm` вычисляет его
итоговый адрес с учётом базы TEXT/DATA модуля и физически записывает значение
в числовой `Float64` operand вложенного PCVM до упаковки `PCDL`. Поэтому
динамический контейнер уже содержит разрешённые межмодульные ссылки; loader
повторяет разрешение по таблице relocation для проверки и совместимости
формата. Интеграционный тест читает вложенный PCOB напрямую и проверяет
исправленный operand до запуска loader.

Для DATA линкер декодирует таблицы сегментов обоих PCVM, вычисляет
`dataExtent = align4(last.address + last.length)` и назначает библиотеке
`dataBase = main.dataExtent`. Это значение применяется к `ABS_DATA`
relocation так же, как `main.textCount` применяется к `ABS_TEXT`. Отдельный
тест создаёт четырёхбайтовую DATA-секцию main и проверяет, что адрес локальных
данных библиотеки изменён с `0` на `4` непосредственно во вложенном PCOB.

Из заголовков вложенных `PCVM` линкер читает `instructionCount` каждого
модуля. Поле `instruction` каждой relocation проверяется условием
`0 <= instruction < instructionCount` до обращения к TEXT. Тест с
индексом `999` подтверждает остановку линковки без создания `a.dyn`.

Линкер также декодирует variable-length TEXT до конкретной инструкции:
учитывает `opcode`, `argc`, числовые operands (`type=0`, 8 байт) и
строковые operands (`type=1`, `length:u16`, UTF-8). Для relocation
проверяется `operand < argc` и обязательный числовой тип слота; найденный
адрес Float64 сохраняется как patch point. Тест с operand index `5` для
однооперандного `CALL` подтверждает отказ без создания контейнера.

До упаковки self-hosted линкер вызывает общую Assembly-процедуру проверки
для каждого модуля. Она проверяет `PCOB` magic, версию, payload size,
число symbols/relocations и равенство полного вычисленного размера
фактическому размеру файла. Повреждённый или обрезанный второй объект
останавливает линковку и `a.dyn` не создаётся; оба случая покрыты
отрицательными интеграционными тестами.

Добавлен статический multi-object режим:

```text
main.obj math.obj --static
```

`linker.asm` объединяет потоки TEXT двух PCOB, исправляет общий
`instructionCount`, добавляет нулевую таблицу сегментов и записывает один
исполняемый `a.bin` в формате `PCVM v2`. Relocation применяются до копирования
TEXT. Интеграционный тест запускает созданный файл и проверяет внешний
`CALL` результатом `42`.

Для динамического контейнера можно явно указать `--dynamic`; без третьего
аргумента двухобъектный режим также остаётся динамическим для совместимости.
Любой другой флаг отклоняется до создания выходного файла.

Статический режим также объединяет DATA-сегменты: пересчитывает общий
`segmentCount`, копирует записи main без смещения и прибавляет
`main.dataExtent` к адресам записей библиотеки. Длины и содержимое сегментов
переносятся без изменения. Интеграционный тест проверяет итоговые записи
`[address=0, data=1,2,3,4]` и `[address=4, data=77]`, а также `ABS_DATA`
operand со значением `4`.

Таким образом, бинарное ядро пункта 6 поддерживает статическую и динамическую
линковку двух PCOB-модулей с TEXT, DATA, imports, exports и relocation.
Следующее расширение — снять ограничение в два входных объекта и добавить
архивный формат библиотек.

## Критерий готовности

Ассемблер считается self-hosted после прохождения полного цикла:

```text
host assembler → assembler.bin
assembler.bin → assembler.obj
self-hosted linker → assembler-2.bin
assembler-2.bin → тестовые .obj
self-hosted linker → тестовые .bin
CPU → ожидаемый результат
```

### Bootstrap текущего состояния

Пока используется плотный DATA image, bootstrap `assembler.asm` требует
компьютер с 2 МиБ RAM:

- `65536` — буфер исходного текста;
- `131072` — формируемый PCVM payload; область начинается после полного
  64-КиБ буфера исходника и не перекрывается большими self-hosted исходниками;
- `393216` — relocation table;
- `425984` — плотный DATA image;
- `1310720` — выходной PCOB.

Self-hosted assembler теперь действительно читает полный `system/assembler.asm`
с диска и создаёт бинарный PCOB собственного исходника. Bootstrap-тест
проверяет результат: payload больше 10 КиБ, более 100 символов и более 300
relocation-записей. Это завершает этап
`host assembler → assembler.bin → assembler.obj`.

Однообъектный путь `linker.asm` теперь валидирует relocation, разрешает
локальные TEXT/DATA-символы и физически патчит payload перед выдачей
`assembler-2.bin`. Ограничения `instructionCount`, `symbolCount` и
`relocationCount` в 255 записей сняты: поля читаются как полноценные u16.
Тест с локальным `JMP` подтверждает, что placeholder заменён и связанный
файл исполняется.

Аргументы `.org`, `.zero` и `.align` теперь принимают как числовые литералы,
так и символы секции CONST, объявленные через `.equ`; разрешение выполняется
одинаково в обоих проходах.

Self-hosted assembler теперь формирует разреженную таблицу DATA. Во втором
проходе `.org` закрывает текущий диапазон `{address, length}` и открывает
следующий; в PCVM записываются только непустые диапазоны. Для собственного
исходника bootstrap-тест проверяет четыре адреса сегментов:
`4096`, `131072`, `1310720`, `5120`. Пустоты между ними в payload отсутствуют.

`STR_TO_INT` поддерживает десятичные и шестнадцатеричные литералы, включая
токены с завершающей запятой (`0x50,`), поэтому второе поколение правильно
восстанавливает magic-заголовки PCVM/PCOB.

Таблица opcode нормализована: записи `.byte opcode, argc` не содержат
inline-комментариев, поэтому потоковый lexer не захватывает следующую
`.dword` как продолжение списка значений. Завершение списков директив
понимает LF (`10`) и CR (`13`), поэтому исходники с LF и CRLF собираются
одинаково.

Полный bootstrap-цикл замкнут:

```text
host assembler → assembler.bin
assembler.bin + linker.bin → assembler2.bin + linker2.bin
assembler2.bin + linker2.bin → assembler3.bin + linker3.bin
assembler3.bin + linker3.bin → generation-three.bin
CPU → 123
```

Вторая генерация больше не подменяется host linker: тест действительно
запускает `linker2.bin` в PCVM, затем третье поколение собирает и исполняет
`LOAD_A 123`, `PRINT_A`, `HALT`.

Обязательные тесты должны покрывать все 134 opcode, прямые и обратные
ссылки, данные, импорты/экспорты, relocation, ошибки символов и повторную
сборку самого ассемблера.
