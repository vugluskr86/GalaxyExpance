# Бортовые компьютеры и Pixel Cosmos Assembly

Бортовой компьютер — устанавливаемый модуль корабля. Сам корпус компьютера не
определяет его вычислительные возможности: они зависят от компонентов во
внутренних слотах.

## Комплектующие

Каждый компьютер имеет следующие слоты:

| Слот | Назначение |
|---|---|
| `GPU` | Режим вывода: текстовый или графический |
| `CPU` | Число потоков — программ, которые могут выполняться параллельно |
| `RAM` | Объём оперативной памяти виртуальной машины |
| `DRIVE` | Постоянное хранилище исходников `.asm` и исполняемых `.bin` |
| `Периферия 1–3` | Универсальные разъёмы накопителей и будущих устройств |

Программа не запустится без установленных CPU, RAM и GPU. DRIVE необходим для
сохранения файлов. CPU исполняет только собранные бинарные файлы `.bin`;
исходник `.asm` напрямую процессору не передаётся.
При замене DRIVE сохранённые на нём программы перемещаются вместе с накопителем.

### Корпуса компьютеров

| Компьютер | Штатный GPU | Штатный CPU | Штатная RAM | Штатный DRIVE |
|---|---|---|---:|---|
| МК-1 «Пролог» | GPU «Литера» | CPU «Такт-1» | 8 КБ | МД-32, 32 КБ |
| МК-2П «Алгол» | GPU «Спектр» | CPU «Такт-4» | 64 КБ | КР-512, 512 КБ |
| МК-3М «Магистраль» | GPU «Спектр» | CPU «Такт-4» | 4 МБ | ЖД-65535 и дисковод ФД-144 |

### Доступные компоненты

GPU:

| ID предмета | Название | Вывод |
|---|---|---|
| `gpu_text` | GPU «Литера» | `text` |
| `gpu_graphics` | GPU «Спектр» | `graphics` |

Текстовый GPU поддерживает только текстовый режим терминала. Графический GPU
поддерживает текстовый и графический режимы, включая пиксели, линии,
прямоугольники и окружности.

CPU:

| ID предмета | Название | Потоки |
|---|---|---:|
| `cpu_single` | CPU «Такт-1» | 1 |
| `cpu_dual` | CPU «Такт-2» | 2 |
| `cpu_quad` | CPU «Такт-4» | 4 |

Число потоков задаёт верхнюю границу одновременно запущенных программ.
Редактор запускает одну программу за нажатие, но исполнитель проверяет лимит
CPU для всех запросов на выполнение.

RAM:

| ID предмета | Название | Объём |
|---|---|---:|
| `ram_8` | RAM ОЗУ-8 | 8 КБ |
| `ram_32` | RAM ОЗУ-32 | 32 КБ |
| `ram_64` | RAM ОЗУ-64 | 64 КБ |

Перед запуском размер бинарного файла сравнивается с объёмом RAM. Этот же объём
выделяется адресному пространству процессора.

DRIVE:

| ID предмета | Название | Тип | Объём |
|---|---|---|---:|
| `drive_magnetic` | Магнитный диск МД-32 | магнитный диск | 32 КБ |
| `drive_chip` | Чип памяти ЧП-128 | чип | 128 КБ |
| `drive_crystal` | Кристалл памяти КР-512 | кристалл | 512 КБ |

Объём DRIVE ограничивает суммарный размер исходников и бинарных файлов. Размер
`.asm` считается в байтах UTF-8, поэтому кириллица обычно занимает больше
одного байта на символ.

### Универсальные накопители

МК-3М «Магистраль» имеет четыре слота `Периферия 1–4`. В них устанавливаются
носители с общим типом слота: дисковод `drive_floppy` (144 КБ) и жёсткий диск
`drive_hard` (2 МБ). Штатная дискета содержит стартовую систему; жёсткий диск
можно использовать как второй загрузочный носитель. Каждый носитель переносит
свои файлы вместе с предметом.

Стартовый инвентарь также содержит загрузочный установочный носитель
`drive_installer` (PCFD-65535, 64 МБ). Установите его в периферийный слот,
выберите в BIOS Setup и загрузитесь с него: `installer.bin` попросит target
DRIVE, пароль root и выбор guest, отформатирует target в PCFS и назначит
`kernel.bin` загрузочным файлом.

После установки консоль монтирует PCFS, поэтому `ls` показывает каталоги
установленной системы (`bin/`, `etc/`, `sbin/`, `usr/`), а не только
загрузочный `kernel.bin`. В `/bin` доступны `cat`, `cp`, `ps`, `chgrp`,
`chown`, `mkdir`, `mv`, `passwd`, `rm`, `top` и `user`.

`cd путь` — встроенная команда этой shell: она меняет текущий каталог консоли
и cwd для следующих запускаемых утилит. Без аргумента `cd` возвращает в `/`.

## Работа с компьютером

1. Откройте экран экипировки корабля клавишей `B`.
2. Установите компьютер в корабельный слот «Борт. компьютер».
3. Установите CPU, RAM, DRIVE и GPU во внутренние слоты компьютера.
4. Нажмите «Программировать».
5. Создайте файл с расширением `.asm`, введите программу и нажмите «Сохранить».
6. Нажмите «Собрать». Ассемблер создаст рядом файл с тем же именем и
   расширением `.bin`.
7. Выберите созданный `.bin` в списке файлов.
8. Нажмите «Запуск».

Бинарный файл в редакторе показывается как шестнадцатеричный дамп и доступен
только для чтения. После изменения исходника его необходимо собрать заново.
Попытка запустить `.asm` завершается сообщением о необходимости сборки.

После выполнения редактор показывает:

- строки, выведенные инструкциями `PRINT`;
- причину остановки или ошибку;
- количество исполненных инструкций;
- активную конфигурацию CPU, RAM и GPU;
- итоговые значения основных регистров.

Под игровым экраном находится отдельный canvas бортового терминала размером
420×420 внутренних пикселей (визуально он имеет ту же ширину, что и игровой
canvas). Клик по терминалу передаёт ему фокус. После этого браузерные события
клавиатуры и мыши поступают в устройство ввода компьютера, а не в управление
кораблём.

При создании нового компьютера на его штатном DRIVE находится пример
`hello.asm`, исходник загрузочной системы `os.asm` и собранная система
`os.bin`, а также диагностическая демосцена `demoscene.asm` и уже собранный
`demoscene.bin`. Выберите `demoscene.bin` в редакторе и нажмите «Запуск»:
сначала в панели результата появится проверка PCVM, RAM и ввода, затем терминал
покажет пятисекундную сцену с FPU-орбитами, линиями, окружностями, цветом и
кадровой анимацией GPU. Для неё требуется GPU «Спектр» с графическим режимом.

## BIOS и загрузка операционной системы

BIOS и его настройки хранятся в отдельной энергонезависимой памяти корпуса и
не занимают место на DRIVE. В ней сохранены исходник программы BIOS, выбранный
загрузочный слот и имя загрузочного файла; эти данные не исчезают при смене
накопителя и подготовлены для будущей перепрошивки.
Откройте меню «Редактировать» установленного компьютера и нажмите «Включить
компьютер». BIOS автоматически:

1. переводит терминал в текстовый режим;
2. показывает текущие дату и время браузера;
3. перечисляет CPU, RAM, GPU и DRIVE с характеристиками;
4. показывает все заполненные и пустые внутренние слоты;
5. перечисляет порты дисплея, клавиатуры, мыши и периферии;
6. ищет на DRIVE исполняемый файл `os.bin`;
7. загружает и исполняет найденную операционную систему.

Нажмите `Del` на сфокусированном терминале, чтобы открыть BIOS Setup. В нём
видны CPU, RAM, все внутренние слоты и установленное оборудование. Стрелками
`↑`/`↓` выбирается загрузочный носитель, `Enter` назначает его. `Esc`
спрашивает, записать ли настройки в энергонезависимую память;
`Enter`/`Y` сохраняет, повторный `Esc`/`N` выходит без сохранения. После выхода
компьютер загружается с выбранного носителя.

Если DRIVE отсутствует или `os.bin` удалён, загрузка останавливается с понятной
ошибкой. Файл BIOS находится в `src/game/bios.js`; пользовательские программы
не могут случайно перезаписать прошивку.

Упрощённый листинг BIOS:

```asm
TERM_MODE text
TERM_COLOR 0x7ee08a, 0x000000
TERM_CLEAR
PRINT "PIXEL COSMOS BIOS 1.0"
SYS_TIME
PRINT "ОБОРУДОВАНИЕ:"
HW_LIST
PRINT "СЛОТЫ:"
SLOT_LIST
PRINT "ПОРТЫ:"
PORT_LIST
PRINT "Поиск загрузочного диска..."
BOOT "os.bin"
HALT
```

### Системные инструкции BIOS

| Команда | Действие |
|---|---|
| `SYS_TIME` | вывести текущие локальные дату и время |
| `HW_LIST` | вывести установленные CPU, RAM, GPU и DRIVE с характеристиками |
| `SLOT_LIST` | вывести все внутренние слоты компьютера и их содержимое |
| `PORT_LIST` | вывести терминал, браузерные устройства ввода и порты периферии |
| `BOOT "file.bin"` | остановить прошивку и запросить запуск бинарного файла с DRIVE |

`BOOT` обрабатывается средой компьютера после остановки текущего процессора.
ОС получает новую, очищенную RAM и сброшенные регистры, но продолжает работать
с тем же терминалом. Поэтому штатная `os.bin`, собранная из `os.asm`, не
очищает экран и оставляет
результаты POST BIOS видимыми.

## Pixel Cosmos OS

После исполнения `os.bin` среда создаёт ядро Pixel OS и запускает shell на
canvas терминала. Кликните по терминалу, введите команду и нажмите Enter.
Backspace редактирует текущую строку.

### Shell

| Команда | Назначение |
|---|---|
| `help` | список команд |
| `ls` | файлы и их размер на DRIVE |
| `ps` | PID, состояние и имя всех процессов |
| `mem` | свободная и общая RAM |
| `run file.bin` | загрузить бинарник и поставить процесс в очередь |
| `kill pid` | удалить ещё не запущенный процесс из очереди |
| `send pid data` | отправить процессу сообщение от shell, PID отправителя `0` |
| `recv pid` | забрать следующее сообщение из очереди процесса |
| `asm source.asm output.obj` | скомпилировать исходник в объектный файл |
| `link output.bin a.obj b.obj ...` | статически слинковать объектные файлы |
| `link output.bin a.obj b.obj ... --dynamic` | создать динамический bundle |
| `time` | локальные дата и время |
| `clear` | очистить терминал |

### Менеджер процессов

Процессы имеют уникальный PID и состояния `ready`, `running`, `exited`,
`failed` или `killed`. Планировщик работает кооперативно в одном браузерном
потоке: готовые процессы помещаются в FIFO-очередь и запускаются
последовательно через задачи event loop. Один процесс не создаёт Web Worker и
не блокирует запуск следующего после своего завершения.

Текущая простая версия выполняет один машинный файл атомарно до `HALT`, ошибки
или лимита инструкций. `kill` поэтому применяется к процессу в состоянии
`ready`; вытесняющая многозадачность и остановка уже выполняющегося процесса
не реализованы.

### Менеджер памяти

Для процесса выделяется непрерывный участок RAM размером с загруженный
бинарник. Используется алгоритм first-fit:

1. блоки сортируются по начальному адресу;
2. выбирается первый подходящий свободный промежуток;
3. после `exited`, `failed` или `killed` блок освобождается.

Команда `mem` показывает состояние распределителя. Если непрерывного блока
нужного размера нет, `run` возвращает ошибку нехватки RAM.

### IPC

У каждого процесса есть FIFO-очередь сообщений. Ядро предоставляет JavaScript
API `ProcessManager.send(from, to, data)` и `receive(pid)`, команды shell
`send`/`recv`, а также системные инструкции Assembly:

| Команда | Действие |
|---|---|
| `OS_PID` | записать PID текущего процесса в `A` |
| `IPC_SEND` | отправить число из `B` процессу с PID из `A` |
| `IPC_RECV` | получить сообщение: PID отправителя в `A`, данные в `B` |

После `IPC_RECV` флаг `Z` сброшен, если сообщение получено, и установлен, если
очередь пуста. В пустом случае `A = 0`, `B = 0`.

```asm
; отправить число 42 процессу 2
LOAD_A 2
LOAD_B 42
IPC_SEND

; прочитать следующее сообщение
IPC_RECV
JZ no_message
PRINT "Sender PID:"
PRINT_A
MOV_A_B
PRINT "Value:"
PRINT_A
no_message:
HALT
```

## Объектные файлы, библиотеки и линкер

Программа `asm` в shell создаёт перемещаемый объект `.obj` формата `PCOB`.
Объект содержит имя модуля, исходник без директив и таблицы импортов/экспортов.

Директивы:

```asm
.import double
.export double
```

Библиотека `examples/lib-math.asm`:

```asm
.export double

double:
MOV_B_A
ADD_A_B
RET
```

Программа `examples/process-main.asm`:

```asm
.import double

main:
LOAD_A 21
CALL double
PRINT_A
HALT
```

Сборка в shell:

```text
pcos$ asm process-main.asm main.obj
pcos$ asm lib-math.asm math.obj
pcos$ link app.bin main.obj math.obj
pcos$ run app.bin
```

Линкер проверяет повторные экспорты и все неразрешённые импорты. При
статической линковке код библиотеки включается в обычный PCVM-бинарник.

Динамическая линковка:

```text
pcos$ link app.dyn main.obj math.obj --dynamic
pcos$ run app.dyn
```

Файл `app.dyn` имеет формат `PCDL` и хранит отдельные модули с таблицами
символов. Загрузчик ОС разрешает внешние символы и создаёт исполняемый PCVM-код
в момент `run`. Это загрузочная динамическая линковка: библиотека остаётся
отдельным модулем в bundle, но после загрузки процесс исполняет единый образ.

Готовые раздельные примеры находятся в `examples`:

- `static-link-main.asm` и `static-link-library.asm` — статический вызов
  экспортированной функции из TEXT;
- `dynamic-link-main.asm` и `dynamic-link-library.asm` — динамический импорт
  символа из DATA;
- `LINKING.md` — команды сборки и ожидаемый результат.

## Ассемблер и машинный код

Кнопка «Собрать» запускает внутриигровой ассемблер. Он выполняет два прохода:

1. разбирает исходник, собирает таблицу меток и подставляет адреса переходов;
2. кодирует инструкции и операнды в бинарный файл формата PCVM.

Формат `.bin`:

| Смещение | Размер | Содержимое |
|---:|---:|---|
| `0` | 4 байта | сигнатура `PCVM` (`50 43 56 4d`) |
| `4` | 1 байт | версия формата, сейчас `01` |
| `5` | 2 байта | число инструкций, `uint16` little-endian |
| `7` | переменный | последовательность машинных инструкций |

Каждая инструкция содержит:

```text
opcode:u8  operandCount:u8  operands...
```

Числовой операнд кодируется как `00` и `Float64` little-endian. Строковый
операнд или имя регистра кодируется как `01`, длина `uint16` и байты UTF-8.
Загрузчик проверяет сигнатуру, версию, opcodes, границы и отсутствие лишних
данных. Повреждённый или несовместимый файл CPU не запускает.

Диапазоны машинных кодов:

| Коды | Группа |
|---|---|
| `01–22` | целые числа, память, переходы и стек |
| `23–35` | float-операции |
| `36–48` | SIMD-векторы |
| `49–4c` | текстовый вывод |
| `4d–56` | терминал, графика и анимация |
| `57–5c` | клавиатура и мышь |
| `5d–64` | BIOS, ОС и системные службы |
| `65` | `HALT` |

Например, `LOAD_A` имеет opcode `01`, `ADD_A_B` — `0f`, `GFX_PIXEL` — `50`,
`BOOT` — `61`, `OS_PID` — `62`, `IPC_SEND` — `63`, `IPC_RECV` — `64`,
`HALT` — `65`. Актуальная полная таблица экспортируется как
`OPCODES` из `src/game/cpu.js`.

## Модель процессора

### Регистры

| Регистры | Тип и назначение |
|---|---|
| `A`, `B`, `C`, `D` | знаковые 32-битные целые числа |
| `FA`, `FB`, `FC`, `FD` | числа с плавающей точкой JavaScript |
| `V0`–`V7` | SIMD-векторы из четырёх чисел |
| `PC` | индекс следующей инструкции |
| `SP` | указатель вершины стека в RAM |
| `Z` | флаг нулевого результата |

Каждый запуск создаёт чистую виртуальную машину: регистры и RAM обнуляются.
Стек растёт от конца RAM к началу.

### Память

RAM адресуется с нуля в байтах. Последний допустимый адрес равен
`объём RAM − 1`.

- `LOAD_M_*` и `STORE_*` читают или записывают один байт.
- `PUSH_A` и `POP_A` используют четыре байта.
- `VLOAD` и `VSTORE` используют 16 байт — четыре компонента `Float32` в формате
  little-endian.
- Выход за границы RAM немедленно останавливает программу с ошибкой.

Адреса и числовые литералы понимают обычную запись JavaScript:

```asm
LOAD_A 42
STORE_A 256
LOAD_M_A 0x100
```

В позициях числовых аргументов также можно использовать регистры `A–D` и
`FA–FD`. Например, `GFX_PIXEL C, D, 0xffffff` берёт координаты из `C` и `D`.

## План защищённого режима процессора

### Цель

Защищённый режим должен отделить ядро Pixel OS от пользовательских программ.
Процесс не должен иметь возможность читать или изменять память другого
процесса, обращаться к DRIVE и устройствам в обход ОС, выполнять инструкции
управления процессором или повреждать контекст ядра.

Текущий режим исполнения без разграничения сохраняется как `real mode` для
BIOS, старых бинарников и bootstrap-инструментов. После загрузки ядро явно
включает `protected mode`.

### Модель привилегий

Предусматриваются два уровня:

| Уровень | Назначение |
|---|---|
| `kernel` | BIOS, ядро ОС, драйверы, планировщик и обработчики исключений |
| `user` | shell-команды и обычные процессы |

В состояние CPU добавляются:

- `MODE` — текущий уровень `kernel/user`;
- `KSP` — отдельный указатель стека ядра;
- `UBASE` — начало физической области текущего процесса;
- `ULIMIT` — размер доступной пользовательской области;
- `IVT` — адрес таблицы обработчиков исключений и системных вызовов;
- `CAUSE` и `FAULT_ADDR` — причина исключения и проблемный виртуальный адрес;
- флаг `IE` — разрешение маскируемых прерываний.

Пользовательская программа видит виртуальные адреса `0..ULIMIT-1`.
Физический адрес вычисляется как `UBASE + virtualAddress`. Ядро продолжает
работать с физической RAM. На первом этапе используется такая сегментная
модель; страничную MMU можно добавить позднее без изменения ABI программ.

### Защита памяти

Все пути доступа к памяти должны проходить через одну функцию трансляции:

- `LOAD_M_*`, `STORE_*`;
- `LOAD8_A_B`, `STORE8_A_B`, `LOAD32_A_B`, `STORE32_A_B`;
- `PUSH_A`, `POP_A`, `CALL`, `RET`;
- SIMD `VLOAD/VSTORE`;
- `MEM_COPY`, строки, файловые и терминальные буферы;
- загрузка статических DATA-сегментов.

В `user`-режиме проверяется весь диапазон операции, а не только первый байт.
Переполнение адреса, выход за `ULIMIT`, отрицательный адрес, неверный `SP` или
пересечение границы процесса создают исключение `MEMORY_FAULT`. Проверка
должна выполняться до чтения или записи, чтобы инструкция была атомарной.

На втором этапе к области добавляются права `R/W/X`:

- TEXT — `R-X`;
- DATA и heap — `RW-`;
- guard page/guard range между heap и stack — `---`;
- стек — `RW-`, без исполнения.

Переход `JMP/CALL/RET` в область без `X` создаёт `EXECUTE_FAULT`, а запись в
TEXT — `WRITE_PROTECTION_FAULT`.

### Привилегированные операции

Прямые операции с оборудованием разрешаются только ядру:

- `BOOT`, `HW_LIST`, `SLOT_LIST`, `PORT_LIST`;
- `FS_LIST`, `FS_READ`, `FS_WRITE`, `FS_DELETE`;
- управление процессами и распределителем памяти;
- изменение `MODE`, `UBASE`, `ULIMIT`, `IVT`, `KSP` и флага прерываний;
- прямое получение браузерного ввода, если устройство закреплено за ОС.

Терминальные и графические команды можно оставить пользовательскими только
после введения дескриптора виртуального терминала. До этого они также должны
вызываться через системный API.

Попытка выполнить привилегированную инструкцию в `user`-режиме создаёт
`PRIVILEGE_FAULT`, а не завершает всю виртуальную машину JavaScript-ошибкой.

### Новые инструкции и ABI

Планируемое минимальное расширение ISA:

| Opcode | Инструкция | Операнды | Режим | Назначение |
|---|---|---:|---|---|
| `87` | `PM_ENABLE` | 0 | kernel | включить защищённый режим |
| `88` | `PM_DISABLE` | 0 | kernel | вернуться в real mode при остановке ОС |
| `89` | `SET_UBASE` | 0 | kernel | установить `UBASE=A` |
| `8a` | `SET_ULIMIT` | 0 | kernel | установить `ULIMIT=A` |
| `8b` | `SET_KSP` | 0 | kernel | установить `KSP=A` |
| `8c` | `SET_IVT` | 0 | kernel | установить `IVT=A` |
| `8d` | `ENTER_USER` | 0 | kernel | войти в user mode с `PC=A`, `SP=B` |
| `8e` | `SYSCALL n` | 1 | user/kernel | синхронно войти в ядро |
| `8f` | `IRET` | 0 | kernel | восстановить сохранённый контекст и режим |
| `90` | `CLI` | 0 | kernel | запретить маскируемые прерывания |
| `91` | `STI` | 0 | kernel | разрешить маскируемые прерывания |
| `92` | `KGET_FAULT` | 0 | kernel | загрузить номер syscall/fault в `A` |
| `93` | `KGET_ARG n` | 1 | kernel | загрузить сохранённый аргумент `A–D` по индексу `0–3` |
| `94` | `KCALL_HOST` | 0 | kernel | вызвать разрешённый аппаратный/VFS механизм текущего trap |
| `95` | `SYSRET` | 0 | kernel | записать `A–D` в context frame и вернуться в user mode |

Добавление opcode требует новой зафиксированной версии ISA и обновления
таблиц host/self-hosted assembler. Старые `PCVM v2` запускаются в real mode;
защищённые бинарники должны явно указывать требуемую версию/feature flags.

Номер системного вызова передаётся операндом `SYSCALL`, аргументы — через
`A–D`, результат — через `A`, код ошибки — через `D`. Строки и структуры
передаются как `{virtualAddress, length}` и обязательно проверяются ядром.

Protected mode обозначается `featureFlags & 0x0001` в PCVM v3. Единственным
нормативным источником числовых констант является
`src/game/protected-mode.js`.

Заголовок PCVM v3 имеет фиксированный вид:

```text
offset  size  field
0       4     magic "PCVM"
4       1     version = 3
5       2     featureFlags, little-endian
7       2     instructionCount, little-endian
9       ...   instruction stream и DATA segment table
```

Если protected feature отсутствует, загрузчик не разрешает opcode `87–91`.
Формат PCVM v2 не меняется и продолжает декодироваться старым путём.

Минимальный набор syscall:

| Группа | Вызовы |
|---|---|
| процессы | `exit`, `yield`, `spawn`, `wait`, `getpid`, `kill` |
| память | `alloc`, `free`, `mem_info` |
| файлы | `open/read/write/close`, `list`, `delete` |
| IPC | `send`, `recv` |
| терминал | `tty_read`, `tty_write`, управление текстовым/графическим режимом |
| время | `time`, таймер ожидания |

Зафиксированные диапазоны syscall: процессы `01–06`, память `10–12`, файлы
`20–25`, IPC `30–31`, терминал `40–42`, время `50–51`.

### Исключения и вход в ядро

Таблица `IVT` содержит адрес обработчика для каждого события:

1. CPU проверяет инструкцию и доступ к памяти.
2. При syscall/исключении сохраняет полный user-контекст в kernel stack:
   `PC`, `SP`, `A–D`, float/SIMD-регистры, флаги и прежний `MODE`.
3. CPU переключает `MODE=kernel`, `SP=KSP`, записывает `CAUSE/FAULT_ADDR`.
4. Выполнение переходит по соответствующему вектору `IVT`.
5. Обработчик завершает процесс или исправляет состояние.
6. `IRET` атомарно восстанавливает контекст и возвращает `MODE=user`.

IVT содержит 64 little-endian записи `u32` и занимает 256 байт. Зафиксированы
коды: `1 MEMORY_FAULT`, `2 EXECUTE_FAULT`, `3 WRITE_PROTECTION_FAULT`,
`4 PRIVILEGE_FAULT`, `5 INVALID_OPCODE`, `6 DIVIDE_BY_ZERO`,
`7 STACK_FAULT`, `8 INVALID_IRET`, `9 DOUBLE_FAULT`, `32 SYSCALL`,
`33 TIMER`.

Фиксированная часть context frame занимает 224 байта и выровнена на 16:

| Offset | Поле |
|---:|---|
| `0..20` | `PC`, `SP`, `A`, `B`, `C`, `D` как `u32` |
| `24` | flags: `Z=1`, `USER=2`, `IE=4` |
| `28..32` | `UBASE`, `ULIMIT` |
| `40..64` | `FA`, `FB`, `FC`, `FD` как `Float64` |
| `72..199` | `V0–V7`, по четыре `Float32` |
| `200..208` | `CAUSE`, `FAULT_ADDR`, `RETURN_DEPTH` |
| `212..223` | reserved |

После offset `224` записываются `RETURN_DEPTH` адресов возврата `u32`, затем
весь frame дополняется до границы 16 байт.

Двойная ошибка во время входа в обработчик завершает текущий процесс. Ошибка
в kernel mode считается panic ядра и выводит диагностический экран.

### Переключение процессов

`PixelOS` должен хранить для каждого процесса:

- полный набор регистров и флагов;
- `UBASE/ULIMIT`;
- kernel stack;
- состояние `ready/running/blocked/faulted/exited`;
- очередь IPC и таблицу открытых файлов;
- лимит оставшихся инструкций временного кванта.

Планировщик переключает контекст при `yield`, блокирующем syscall, завершении,
исключении или срабатывании таймера. Несколько процессов в одном аппаратном
потоке выполняются квантами; количество установленных CPU threads определяет
число одновременно активных виртуальных CPU.

### Реализация этапа 2

В CPU добавлены `MODE`, `UBASE`, `ULIMIT`, `KSP`, `IVT`, `IE`, методы
`configureProtectedMode()` и `enterUserMode()`. После reset процессор
находится в совместимом `real mode`.

В `user mode` метод `addr()` принимает виртуальный диапазон, проверяет его
целиком относительно `ULIMIT` и возвращает `UBASE + virtualAddress`.
Проверка использует форму `length <= limit - address`, поэтому сложение
адреса и размера не может обойти границу переполнением.

Через трансляцию проходят:

- прямые, косвенные, 16/32/64-битные и SIMD-доступы;
- user stack, при этом `SP` остаётся виртуальным;
- `MEM_COPY/MEM_CMP`;
- FS, TTY и process buffers;
- строковые операции, tokenizer и lexer;
- загрузка DATA-сегментов.

Строковые инструкции возвращают виртуальные cursor values, хотя сканируют
физический `Uint8Array`. Добавлены тесты ненулевой `UBASE`, полной границы
многобайтовой операции, отрицательных адресов, стека, SIMD, копирования,
TTY, tokenizer и lexer. На этапе 2 нарушение границы ещё выбрасывает ошибку;
преобразование ошибки в `MEMORY_FAULT` через IVT выполняется на этапе 3.

### Реализация этапа 3

В `CPU` добавлен тип `CPUFault`. Любая ошибка адресации в user mode создаёт
`MEMORY_FAULT`; проверка `requireKernel()` создаёт `PRIVILEGE_FAULT`. Цикл
исполнения перехватывает только аппаратные исключения этого типа. Обычные
ошибки JavaScript не маскируются и продолжают означать дефект эмулятора.

При исключении CPU:

1. сохраняет адрес вызвавшей fault инструкции, виртуальный `SP`, `A–D`,
   `FA–FD`, `V0–V7`, `Z`, `IE`, `UBASE/ULIMIT` и весь стек адресов `CALL`;
2. выделяет выровненный context frame вниз от `KSP`;
3. записывает `CAUSE` и `FAULT_ADDR`;
4. атомарно переключается в kernel mode и загружает `PC` из
   `IVT + CAUSE * 4`.

Метод CPU `interruptReturn()` реализует семантику `IRET`: проверяет целостность
frame, восстанавливает полный контекст и возвращает процесс в user mode.
Машинный opcode `IRET` подключается к декодеру PCVM v3 вместе с остальными
зафиксированными protected-mode opcode на этапе 5.

Fault, возникший во время выполнения kernel-кода, не создаёт второй user frame
и завершает выполнение как `kernel panic`. Это предотвращает рекурсивное
повреждение kernel stack. Тесты проверяют переход по IVT, точный адрес fault,
полное восстановление integer/float/SIMD-регистров, флагов, `CALL` stack,
`KSP`, а также `PRIVILEGE_FAULT` и kernel panic.

### Реализация этапа 4

В CPU добавлен синхронный kernel-диспетчер `systemCall(number, returnPC)`.
В protected mode вызов проходит тот же безопасный путь, что исключение:

1. CPU создаёт полный context frame с причиной `SYSCALL`;
2. переключается из user mode в kernel mode;
3. диспетчер проверяет аргументы и все переданные диапазоны памяти;
4. результат записывается в сохранённые `A–D`;
5. `IRET` восстанавливает user-контекст и продолжает исполнение с `returnPC`.

ABI результата: `A` содержит значение или `-1`, `D` — ноль либо отрицательный
код ошибки. Зафиксированы ошибки `NOT_FOUND=-2`, `IO=-5`, `BAD_FILE=-9`,
`BAD_ADDRESS=-14`, `BUSY=-16`, `INVALID=-22`, `NOT_SUPPORTED=-38`.
Неверный указатель не позволяет kernel-коду обратиться к чужой памяти:
диспетчер возвращает `BAD_ADDRESS`.

Реализованы группы syscall:

- процессы: `exit`, `yield`, `spawn`, `wait`, `getpid`, `kill`;
- память: `alloc`, `free`, `mem_info` (неподдерживаемый backend возвращает
  `NOT_SUPPORTED`);
- DRIVE: `read`, `write`, `list`, `delete`; ABI дескрипторов `open/close`
  зарезервирован;
- IPC: `send`, `recv`;
- терминал: `tty_read`, `tty_write`, переключение text/graphics;
- время: `time`, `sleep`.

Прямые инструкции FS, process, IPC, BIOS/hardware, terminal, graphics и input
теперь являются привилегированными в user mode и создают
`PRIVILEGE_FAULT`. В real mode они сохранены без изменений для совместимости
с PCVM v2, BIOS и текущими self-hosted инструментами. Машинное кодирование
инструкции `SYSCALL n` в PCVM v3 будет подключено на этапе 5; CPU-примитив,
kernel ABI и проверка безопасности уже реализованы и протестированы.

### Реализация этапа 5

Host и self-hosted toolchain поддерживают два исполняемых формата:

- PCVM v2 сохраняет старый семибайтный заголовок и 134 legacy opcode;
- PCVM v3 использует девятибайтный заголовок, `featureFlags` и opcode
  `0x87–0x91`.

Host assembler автоматически выбирает v3 при директиве `.protected` или при
использовании любой protected-инструкции. Для обычного исходника он продолжает
выдавать PCVM v2. Декодер сохраняет `version` и `featureFlags` в описании
программы, отклоняет неизвестные версии и запрещает protected opcode без
флага `0x0001`.

К CPU подключены `PM_ENABLE`, `PM_DISABLE`, `SET_UBASE`, `SET_ULIMIT`,
`SET_KSP`, `SET_IVT`, `ENTER_USER`, `SYSCALL n`, `IRET`, `CLI`, `STI`,
`KGET_FAULT`, `KGET_ARG`, `KCALL_HOST` и `SYSRET`.
Привилегированные инструкции используют `requireKernel()`, а `SYSCALL n`
использует dispatcher этапа 4.

Self-hosted `assembler.asm` содержит таблицу из 149 записей: 134 legacy и
15 protected opcode. Он выпускает PCVM v3 payload внутри совместимого PCOB v2.
Self-hosted `linker.asm` вычисляет размер заголовка каждого входного PCVM,
поэтому принимает payload v2 и v3. Статическая multi-object линковка выпускает
PCVM v3; динамический loader объединяет feature flags модулей.

Формат PCOB не изменён: его версия описывает таблицы symbol/relocation, а
версия ISA и feature flags находятся во вложенном PCVM payload. Тесты
проверяют v2/v3, protected opcode и полный self-hosted bootstrap.

### Реализация этапа 6

Штатная `os.bin` теперь является PCVM v3 protected-бинарником и начинает
загрузку с `PM_ENABLE`. После bootstrap объект `PixelOS` работает как
kernel-side менеджер процессов и системных сервисов.

Loader определяет режим по заголовку executable:

- PCVM v3 с `protected feature` загружается как user-процесс;
- PCVM v2 запускается старым real-mode путём совместимости.

Для каждого защищённого процесса создаётся отдельный CPU и фиксированная
физическая раскладка:

```text
0x0000..0x00ff   IVT: 64 записи u32
0x0100..0x0fff   kernel stack
0x1000..RAM-1    user memory, виртуальные адреса 0..ULIMIT-1
```

Loader заполняет все IVT-векторы адресом kernel fault handler, устанавливает
`KSP=0x1000`, `IVT=0`, `UBASE=0x1000`, вычисляет `ULIMIT`, загружает DATA
относительно `UBASE` и вызывает `enterUserMode(PC=0, SP=ULIMIT)`. Protected
process требует минимум 8 КиБ RAM.

В process descriptor сохраняются:

- признак `protected`;
- раскладка IVT/kernel stack/user memory;
- объект CPU и полный контекст;
- `cause` и `faultAddress`;
- состояние `ready/running/faulted/exited`.

Если user-код создаёт исключение, CPU переходит по IVT в kernel handler.
`ProcessManager` помечает только этот процесс как `faulted`, сохраняет
диагностику и освобождает его блок памяти. Нормальный `HALT` в user mode
завершает процесс со статусом `exited`. Syscall возвращается через IRET и
не считается аварией.

DATA-сегменты теперь явно загружаются loader как для protected, так и для
legacy machine. Интеграционные тесты проверяют syscall `getpid`, виртуальную
DATA-адресацию, IVT, отдельный kernel stack, возврат памяти и изоляцию
привилегированного fault.

### Реализация этапа 7

`ProcessManager` использует round-robin scheduler. После выбора процесса
курсор передвигается к следующей записи, поэтому первый бесконечный процесс
не может постоянно выбираться вместо остальных. Стандартный квант равен
1000 инструкциям и доступен как `ProcessManager.quantum`.

При исчерпании кванта protected-процесса с разрешёнными прерываниями CPU:

1. не выполняет следующую инструкцию;
2. создаёт обычный полный context frame с причиной `TIMER`;
3. переключается в kernel mode;
4. возвращает scheduler результат `preempted=true`.

Process descriptor получает `context` с типом `timer`, адресом frame,
сохранёнными user `PC/SP` и признаком `pendingIret`. Процесс переводится из
`running` обратно в `ready`, а счётчик `preemptions` увеличивается.

При следующем выборе этого процесса scheduler сначала выполняет
`interruptReturn()`. Восстанавливаются integer, float и SIMD-регистры, флаги,
user stack, `CALL` stack, `UBASE/ULIMIT`, `PC` и interrupt-enable state.
После этого начинается новый квант. Старый frame освобождается восстановлением
`KSP`, поэтому последовательные вытеснения не накапливают kernel frames.

Legacy PCVM v2 также вытесняется по лимиту инструкций, но без TIMER frame:
его состояние уже хранится в экземпляре CPU и descriptor получает контекст
типа `legacy`.

Fault имеет приоритет над плановым вытеснением. Процесс, перешедший в kernel
handler с причиной, отличной от `TIMER` и `SYSCALL`, получает состояние
`faulted`, диагностические `cause/faultAddress`, ненулевой exit code и
освобождение памяти. Остальные процессы продолжают планироваться.

Интеграционный тест запускает бесконечный и короткий protected-процессы на
одном scheduler: первый дважды вытесняется, второй завершается между его
квантами, а первый оба раза использует один и тот же освобождаемый kernel
stack frame.

### Реализация этапа 8

Protected loader создаёт карту доступа для каждого процесса. PCVM использует
раздельные пространства инструкций и данных: TEXT адресуется индексами
инструкций, а LOAD/STORE работают с виртуальной RAM. Поэтому права задаются
так:

| Область | Права | Назначение |
|---|---|---|
| TEXT | `R/X` | пользовательские инструкции до kernel fault handler |
| heap/data | `R/W` | DATA-сегменты, heap и syscall-буферы |
| guard | нет прав | 256 байт между heap и stack |
| stack | `R/W`, NX | последние 1–4 КиБ user memory |

CPU проверяет execute permission перед каждым fetch, включая цель `JMP`,
`JZ`, `JNZ`, `CALL`, `RET` и восстановленный `PC`. Переход за предел
user TEXT создаёт `EXECUTE_FAULT`. Добавленный loader-ом fault handler не входит
в user TEXT и исполняется только после переключения в kernel mode.

`addr()` теперь принимает тип доступа `read`, `write` или `stack`. Проверкой
записи охвачены:

- прямые и косвенные STORE 8/16/32/64;
- SIMD store;
- destination `MEM_COPY`;
- FS, process и TTY output buffers;
- буферы, заполняемые syscall.

Каждый диапазон проверяется целиком и должен помещаться в одну область с
нужными правами. Пересечение guard или иной запрещённой области создаёт
`MEMORY_FAULT`. Неверный syscall-буфер возвращает `BAD_ADDRESS`.

`PUSH/POP` используют отдельный stack access. Выход `SP` ниже начала stack или
выше `ULIMIT` создаёт `STACK_FAULT`. Stack не имеет execute permission; размер
равен четверти доступной user RAM, но ограничен диапазоном 1–4 КиБ.

Тесты проверяют невозможность выполнить loader kernel handler из user mode,
отсутствие `W` у TEXT, NX stack, запись в guard range и переполнение stack.

### Реализация этапов 9 и 10

`system/shell.asm` и все `.asm` из `examples/` теперь содержат `.protected`.
Пользовательский код больше не использует прямые инструкции `TERM_*`, `GFX_*`,
`IN_*`, `FS_*`, `PROC_*`, `IPC_*`, `OS_PID` и `MEM_INFO`.

Syscall ABI расширен:

| Диапазон | Новые вызовы |
|---|---|
| `07` | `process_list` |
| `43–44` | `tty_clear`, `tty_color` |
| `60–66` | pixel, line, rect, circle, begin/frame/end animation |
| `70–74` | keyboard, mouse x/y/buttons/wheel |

Shell использует syscall для чтения строки, списка файлов и процессов,
информации о памяти, запуска/остановки процессов, очистки терминала и `yield`.
`SYSCALL yield` завершает текущий квант и возвращает управление scheduler.

Графические syscall используют текущий цвет терминала, задаваемый
`tty_color`. Линия принимает `A–D = x1,y1,x2,y2`, прямоугольник —
`x,y,w,h`, окружность — `x,y,radius,fill`. Лиссажу сохраняет счётчик на
user stack и создаёт 256 кадров из настоящего user-процесса.

BIOS остаётся PCVM v2 и выполняется в real mode. Загруженная `os.bin` является
PCVM v3 и включает kernel mode. Команда PixelOS `asm` автоматически добавляет
`.protected`, если исходник не выбрал режим явно, поэтому новые программы ОС
по умолчанию собираются как protected PCVM v3. Старые готовые PCVM v2
по-прежнему запускаются совместимым real-mode loader.

Итоговая матрица тестов охватывает:

- границы user RAM и неверные syscall pointers;
- privilege, execute, stack и memory faults;
- R/W/X, NX stack и guard range;
- IVT, полный IRET context и kernel panic;
- TIMER preemption и round-robin;
- статическую/динамическую линковку PCVM v2/v3;
- protected shell без прямых аппаратных opcode;
- все bundled-примеры и user-mode анимацию Лиссажу;
- BIOS real mode → OS kernel mode → процессы user mode;
- полный self-hosted bootstrap assembler/linker.

Protected mode включён по умолчанию для новой ОС.

### Критерии готовности

Защищённый режим считается завершённым, когда тесты подтверждают:

- процесс не читает и не изменяет память ядра или соседнего процесса;
- выход за виртуальную память завершает только виновный процесс;
- пользовательский код не выполняет привилегированные инструкции;
- syscall сохраняет и восстанавливает все регистры, включая SIMD;
- неверный user pointer безопасно возвращает ошибку или создаёт fault;
- бесконечный процесс вытесняется по кванту и не блокирует остальные;
- shell, assembler, linker и обычные программы работают в user mode;
- BIOS и старые PCVM v2 продолжают запускаться в совместимом real mode.

## Синтаксис Assembly

- Одна инструкция записывается на строке.
- Регистр не зависит от регистра букв: `v0` и `V0` равнозначны.
- Аргументы можно разделять пробелами или запятыми.
- Комментарий начинается с `;` и продолжается до конца строки.
- Метка состоит из латинских букв, цифр и `_`, не может начинаться с цифры и
  завершается двоеточием.
- Строка для `PRINT` должна быть корректной строкой JSON в двойных кавычках.

```asm
; обратный отсчёт
LOAD_A 3

loop:
PRINT_A
DEC_A
JNZ loop
HALT
```

Переход может использовать метку или прямой индекс инструкции:

```asm
JMP finish
NOP
finish: HALT
```

## Система команд

### Загрузка и копирование целых чисел

| Команда | Действие |
|---|---|
| `LOAD_A n` | `A = n`, обновить `Z` |
| `LOAD_B n` | `B = n` |
| `LOAD_C n` | `C = n` |
| `LOAD_D n` | `D = n` |
| `MOV_A_B` | `A = B`, обновить `Z` |
| `MOV_A_C` | `A = C`, обновить `Z` |
| `MOV_A_D` | `A = D`, обновить `Z` |
| `MOV_B_A` | `B = A` |
| `MOV_C_A` | `C = A` |
| `MOV_D_A` | `D = A` |

### Целочисленная память и стек

| Команда | Действие |
|---|---|
| `LOAD_M_A address` | загрузить байт RAM в `A`, обновить `Z` |
| `LOAD_M_B address` | загрузить байт RAM в `B` |
| `STORE_A address` | записать младший байт `A` в RAM |
| `STORE_B address` | записать младший байт `B` в RAM |
| `PUSH_A` | положить 32-битное значение `A` на стек |
| `POP_A` | снять значение со стека в `A`, обновить `Z` |

### Целочисленная арифметика

| Команда | Действие |
|---|---|
| `ADD_A_B` | `A = A + B` |
| `ADD_A_C` | `A = A + C` |
| `SUB_A_B` | `A = A - B` |
| `SUB_A_C` | `A = A - C` |
| `MUL_A_B` | `A = A × B` |
| `DIV_A_B` | `A = trunc(A / B)` |
| `AND_A_B` | побитовое `A = A & B` |
| `OR_A_B` | побитовое `A = A \| B` |
| `XOR_A_B` | побитовое `A = A ^ B` |
| `CMP_A_B` | обновить `Z` по результату `A − B`, не меняя `A` |
| `INC_A` | увеличить `A` на один |
| `DEC_A` | уменьшить `A` на один |

Арифметические операции над `A` обновляют флаг `Z`. Деление на ноль завершает
программу ошибкой.

### Управление выполнением

| Команда | Действие |
|---|---|
| `JMP label` | безусловный переход |
| `JZ label` | переход, если `Z = true` |
| `JNZ label` | переход, если `Z = false` |
| `CALL label` | вызвать подпрограмму |
| `RET` | вернуться из последнего `CALL` |
| `NOP` | ничего не делать |
| `HALT` | штатно остановить процессор |

`RET` без соответствующего `CALL` является ошибкой. Выполнение также
останавливается при выходе `PC` за пределы программы.

### Числа с плавающей точкой

| Команда | Действие |
|---|---|
| `LOAD_F n` | `FA = n` |
| `LOAD_FB n` | `FB = n` |
| `LOAD_FC n` | `FC = n` |
| `LOAD_FD n` | `FD = n` |
| `ITOF` | `FA = A` |
| `FTOI` | `A = trunc(FA)`, обновить `Z` |
| `FADD_FA_FB` | `FA = FA + FB` |
| `FSUB_FA_FB` | `FA = FA - FB` |
| `FMUL_FA_FB` | `FA = FA × FB` |
| `FDIV_FA_FB` | `FA = FA / FB` |
| `FCMP_FA_FB` | обновить `Z` по результату `FA − FB` |
| `FABS_FA` | абсолютное значение `FA` |
| `FNEG_FA` | изменить знак `FA` |
| `FSQRT_FA` | квадратный корень |
| `FSIN_FA` | синус `FA` в радианах |
| `FCOS_FA` | косинус `FA` в радианах |
| `FLOOR_FA` | округлить вниз |
| `FCEIL_FA` | округлить вверх |
| `FROUND_FA` | округлить до ближайшего целого |

### SIMD-векторы

Все векторные регистры содержат четыре компонента: `[x, y, z, w]`.

| Команда | Действие |
|---|---|
| `VSET Vd, x, y, z, w` | записать четыре значения в `Vd` |
| `VLOAD Vd, address` | загрузить `Vd` из 16 байт RAM |
| `VSTORE Vd, address` | сохранить `Vd` в 16 байт RAM |
| `VMOV Vd, Vs` | скопировать `Vs` в `Vd` |
| `VADD Vd, Vs` | покомпонентное сложение |
| `VSUB Vd, Vs` | покомпонентное вычитание |
| `VMUL Vd, Vs` | покомпонентное умножение |
| `VDIV Vd, Vs` | покомпонентное деление; деление на ноль даёт `0` |
| `VDOT Vd, Vs` | скалярное произведение, результат в `FA` |
| `VCROSS Vd, Vs` | трёхмерное векторное произведение, `w = 0` |
| `VNORM Vd` | нормализовать вектор |
| `VLEN Vd` | длина вектора, результат в `FA` |
| `VLERP Vd, Vs` | интерполяция от `Vd` к `Vs`, коэффициент в `FA` |
| `VSCALE Vd` | умножить все компоненты на `FA` |
| `VNEG Vd` | изменить знак всех компонентов |
| `VABS Vd` | взять модуль каждого компонента |
| `VSPLAT Vd` | заполнить все компоненты значением `FA` |
| `VSUM Vd` | сумма компонентов, результат в `FA` |
| `VAVG Vd` | среднее компонентов, результат в `FA` |

Для совместимости с исходным примером поддерживаются составные мнемоники:

```asm
VLOAD_V0 256       ; то же, что VLOAD V0, 256
VSTORE_V0 272      ; то же, что VSTORE V0, 272
VADD_V0_V1         ; то же, что VADD V0, V1
VSCALE_V0          ; то же, что VSCALE V0
VEC_SUM_V0         ; то же, что VSUM V0
```

Составная форма доступна для `VLOAD`, `VSTORE`, `VMOV`, `VADD`, `VSUB`,
`VMUL`, `VDIV`, `VDOT`, `VCROSS`, `VNORM`, `VLEN`, `VSCALE`, `VNEG`,
`VABS`, `VSPLAT`, `VSUM` и `VAVG`.

### Вывод

| Команда | Действие |
|---|---|
| `PRINT "текст"` | вывести строковый литерал |
| `PRINT_A` | вывести `A` |
| `PRINT_FA` | вывести `FA` |
| `PRINT_V Vn` | вывести векторный регистр |

`PRINT` одновременно пишет в результат запуска редактора и в текстовый canvas
терминала. Каждая команда начинает новую строку.

## Терминал

### Режимы и цвет

| Команда | Действие |
|---|---|
| `TERM_MODE text` | включить текстовый режим и очистить экран |
| `TERM_MODE graphics` | включить графический режим и очистить экран |
| `TERM_CLEAR` | очистить терминал текущим цветом фона |
| `TERM_COLOR fg, bg` | установить цвет текста/рисования и цвет фона |

Цвет задаётся числом `0xRRGGBB`, например `0x7ee08a`. Аргумент фона у
`TERM_COLOR` необязателен. Режим `graphics` требует GPU с характеристикой
`graphics`; на GPU «Литера» такая программа завершится ошибкой.

### Графические команды

Координаты отсчитываются от левого верхнего угла: `x` растёт вправо, `y` —
вниз. Размер поверхности — 420×420 пикселей.

| Команда | Действие |
|---|---|
| `GFX_PIXEL x, y, color` | нарисовать пиксель |
| `GFX_LINE x1, y1, x2, y2, color` | нарисовать линию |
| `GFX_RECT x, y, w, h, color, fill` | прямоугольник |
| `GFX_CIRCLE x, y, radius, color, fill` | окружность |
| `GFX_BEGIN` | начать запись кадров анимации |
| `GFX_FRAME delay` | завершить кадр, `delay` — задержка в миллисекундах |
| `GFX_END` | закончить запись и запустить воспроизведение |

`fill` равен `0` для контура и любому ненулевому значению для заливки. Все
`GFX_*` требуют графический GPU. Рисование в текстовом режиме игнорируется,
поэтому перед ним следует выполнить `TERM_MODE graphics`.

Между `GFX_BEGIN` и `GFX_END` графические команды не рисуются сразу, а
записываются в последовательность кадров. `GFX_FRAME` сохраняет команды
текущего кадра. После `GFX_END` терминал воспроизводит их через браузерный
таймер, не блокируя игровой цикл. Если кадры не очищают экран, изображение
накапливается — так анимированный пример Лиссажу постепенно достраивает кривую.

### Клавиатура и мышь

| Команда | Результат |
|---|---|
| `IN_KEY` | забрать следующую клавишу из очереди, её browser keyCode записать в `A` |
| `IN_CHAR` | забрать следующую клавишу, Unicode-код первого символа записать в `A` |
| `IN_MOUSE_X` | координата мыши `x` в `A` |
| `IN_MOUSE_Y` | координата мыши `y` в `A` |
| `IN_MOUSE_BUTTONS` | битовая маска нажатых кнопок в `A` |
| `IN_MOUSE_WHEEL` | накопленное направление колеса в `A`, затем сбросить его |

Если очередь клавиатуры пуста, `IN_KEY` и `IN_CHAR` возвращают `0`. Каждая из
этих команд извлекает одно событие. Для `IN_MOUSE_BUTTONS` используются
браузерные биты: `1` — левая кнопка, `2` — правая, `4` — средняя. Все команды
ввода обновляют флаг `Z`.

Выполнение Assembly не блокирует игровой цикл и не ждёт событие. Терминал
накапливает ввод, а программа опрашивает его при запуске. Для проверки ввода:

1. кликните по canvas терминала;
2. нажмите клавишу или переместите мышь;
3. запустите программу из редактора.

## Ошибки и ограничения

Исполнитель сообщает номер строки для ошибок сборки, например неизвестной
команды, неверного регистра или числового литерала.

Выполнение прерывается при:

- отсутствии CPU, RAM или GPU;
- превышении объёма RAM исходным текстом;
- обращении за пределы RAM;
- целочисленном или float-делении на ноль;
- `RET` без `CALL`;
- превышении лимита в 100 000 инструкций;
- попытке запустить больше программ, чем допускает число потоков CPU.
- использовании графического режима или `GFX_*` без графического GPU.

Лимит инструкций защищает игру от зависания на бесконечном цикле:

```asm
forever:
JMP forever
```

## Утилиты PCOS и сканер

Утилиты `ls`, `cat`, `grep`, `cp`, `mv`, `mkdir`, `rm`, `link`, `chown`,
`chgrp`, `user`, `find` и `ps` установлены как отдельные `.bin`-файлы. Их
короткие точки входа в `system/unix/bin/` намеренно используют общую
Assembly-библиотеку `system/unix/lib/utilities.asm`: при сборке библиотечный
код линкуется внутрь каждого итогового бинарника. В частности, `grep` реально
читает файл, поддерживает `grep [-n] pattern file`, печатает совпавшие строки
и возвращает `0` при совпадении, `1` при его отсутствии.

`scanner` находится в `/usr/bin/scanner.bin` и является отдельной Assembly
программой для сканирования звёздной системы. Она переключает терминал в
графический режим, строит стартовый спектр/equalizer и затем через ограниченный
`SCANNER_OPEN (0x55)` открывает интерактивную радиопанель. В ней настраиваются
частота, направление антенны, ширина луча, поляризация, RX/TX и объём данных;
результат сохраняется в данных мира. Программа работает только из установленного
компьютера в активной системе: без контекста системы она завершится с явной
ошибкой и не создаст ложных данных. Для фактического сканирования цели нужны
сканер, компьютер и антенна, а для исследования поверхности — также зонд.

Сканер и антенна являются самостоятельными сетевыми устройствами. Перед первым
сканированием откройте программу `scanner`, выдайте IP-адреса через подключённый
коммутатор и в разделе «Сеть» укажите IP сканера и IP антенны. Компьютер должен
иметь NIC и свой DHCP-адрес; оба устройства должны быть соединены кабелями с
коммутатором. GUI сканера запрашивает телеметрию от этих адресов по сети и не
запускает анализ при отсутствии маршрута. В GUI коммутатора доступны таблица
DHCP-аренд с MAC-адресами, включение DHCP/DNS, подсеть, время аренды и DNS-домен.
